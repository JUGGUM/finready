## 왜 남기나

프롬프트 튜닝은 실행할 때마다 돈과 시간이 들고, **무엇을 이미 시도했는지 잊으면 같은 것을
다시 시도하게 된다.** 특히 아래 두 가지는 기록이 없으면 반드시 다시 헤맨다.

- 어떤 수정이 효과가 있었고 어떤 것이 없었는지
- 어떤 불일치가 **프롬프트 문제가 아니라 라벨 문제**로 의심되는지

## 버전 이력

| 버전 | 바꾼 것 | 결과 |
|---|---|---|
| `coverage-v1` / `verifier-v1` | 최초 | R01 오판, R03 근거 오염, effort 미설정(기본 high) |
| `coverage-v2` | Risk 카탈로그를 user → **system**(캐싱), 핵심/부연 원칙, NOT_FOUND 정당화, Risk 경계 규칙, effort=medium, reason 60자 | **R01 해결.** R03 미해결. R02 회귀 |
| `verifier-v2` | effort 명시(high), reason 60자 | — |
| `verifier-v3` | **핵심/부연 원칙을 분류기와 통일**, "이미 내려진 판정을 다시 하지 않는다" 명시 | **R04 해결** |

## 해결된 것

**R01 — 과도한 기준 (v2에서 해결)**

v1은 `fact` 전체를 요구 사항으로 읽어, 원금 손실을 명확히 고지했는데도 65% 조건이
없다는 이유로 INSUFFICIENT를 줬다.

원인은 "숫자를 요구했다"가 아니라 **`fact` 안에서 핵심과 부연을 구분할 방법을 안 준 것**이다.
그래서 일반 원칙을 넣었다 — *핵심 = 고객이 무엇을 잃을 수 있는지 / 부연 = 그것을 계산하는
방법(수치·산식·차수·평가 시점)*. R02처럼 수치 자체가 불이익인 경우도 함께 명시해서
"숫자는 항상 부연"으로 잘못 읽히지 않게 했다.

3회 실행 모두 EXPLAINED로 안정적이다.

**R04 — 두 프롬프트가 서로 다른 잣대 (v3에서 해결)**

`coverage-v2`에만 핵심/부연 원칙을 넣고 Verifier에는 안 넣어서, **분류기가 EXPLAINED로
판정한 것을 Verifier가 옛 기준으로 다시 깎았다.**

```
classifierStatus: EXPLAINED
coverageStatus:   INSUFFICIENT   ← Verifier가 "단일 시점 기준이 빠졌다"며 깎음
```

Verifier 프롬프트에 이미 `"이 위험이 설명되었는가"를 다시 판정하지 않는다`고 적혀 있었지만
실제로는 완결성을 재판정하고 있었다. 같은 핵심/부연 기준을 넣고 그 문장을 강화하니 복구됐다.

**교훈: 두 단계가 같은 대상을 판정하면 기준도 같이 바뀌어야 한다.** 한쪽만 고치면
경계 케이스에서 서로 밀어내며 결과가 흔들린다.

## 미해결

**R03 — Risk 간 근거 오염 (모델 오판)**

상담문에 조기상환 얘기가 전혀 없는데, R06의 근거 문장
("지수가 세 개라서 조건이 조금 더 까다로울 수는 있습니다")을 R03 근거로 가져다 쓴다.
`v2`에 경계 규칙("인용하려는 문장이 다른 항목 주제에 더 가까우면 NOT_FOUND")을 넣었지만
R03↔R06에는 안 걸렸다.

**라벨이 맞고 모델이 틀렸다** — 상담문에 조기상환 관련 서술이 없다는 것은 명확하다.

**R02 — 실행마다 뒤집힘**

NOT_FOUND ↔ INSUFFICIENT를 오간다. `v2`의 경계 규칙("한 문장을 여러 항목에 재사용하지
않는다")과 "원금 손실이 발생할 수 있다가 손실 범위를 언급한 것인가" 사이의 긴장이 원인이다.
`v3`에서도 흔들린다 — 프롬프트 충돌이 원인이 아니었다.

**R06 — 라벨 재검토 대상**

3회 실행 모두 INSUFFICIENT로 **일관되게** 라벨(EXPLAINED)과 어긋난다.
모델 근거: *"까다롭다고만 했고, 하나라도 미충족 시 조기상환 불가라는 핵심 불이익을
설명하지 않았다"* — 상담문을 보면 실제로 그 불이익은 나오지 않는다.

**모델이 일관되고 라벨은 사람 한 명의 판단이라면 라벨 쪽을 의심할 차례다.**
`CONS_A_001`은 기존에 있던 시나리오라 라벨 근거가 남아 있지 않다.
데이터셋 확충 때 함께 결정할 것.

## 판정 안정성

같은 프롬프트·같은 입력을 3회 돌린 결과, **경계 케이스는 실행마다 바뀐다.**

| | 안정 | 불안정 |
|---|---|---|
| Risk | R01·R04·R05·R07·R08·R09 | R02·R03 |
| 성격 | 명확한 판정(설명함/언급 없음) | 판단이 갈리는 경계 |

무작위가 아니라 **경계에 집중된 흔들림**이다. `temperature: 0`인데도 그렇다.

**Gate 결과는 3회 모두 정확했다** — `blockingRiskIds [R02, R03, R08]`이
`expectedGateReason`과 일치. 개별 Risk 상태가 어긋나도 제품이 내리는 판단은 맞았다.
평가 지표를 개별 Risk 정확도만으로 잡으면 이 사실이 안 보인다.

## 비용 — 실측 (중요)

**사전 추정이 자릿수로 틀렸다.** 튜닝 착수 전 "세션당 $0.2~0.4, $5면 십몇~스무 세션"으로
추정했으나, 실측은 그 1/5~1/8이다. 한국어 토큰 비율을 과대평가했고(실측 대략 1글자=1토큰)
배치 호출의 효율을 과소평가했다.

`$3/$15` per MTok, 캐시 쓰기 1.25배 / 읽기 0.1배 기준:

| | 콜드(캐시 쓰기) | 웜(캐시 읽기) |
|---|---|---|
| CLASSIFY | $0.0231 | $0.0126 |
| VERIFY | $0.0117 | $0.0068 |
| **Coverage 합계** | **$0.0348** | **$0.0194** |

캐시로 **44% 절감**. 세션 전체(질문 생성·답변 판정 포함) 추정 **~$0.047**,
$5 크레딧으로 **약 100세션**.

**웜 상태에서 비용의 70%가 출력 토큰이다.** 입력은 캐시로 거의 사라졌다.
출력의 대부분은 evidence 인용문이므로, 더 줄이려면 인용을 짧게 해야 하는데
그러면 provenance 유일성이 떨어져 AMBIGUOUS 위험이 오른다. 지금은 건드리지 않는다.

## 캐시

```
1회차: cacheWrite=2969, cacheRead=0
2회차: cacheWrite=0,    cacheRead=2969   ← 완전 적중
```

쓴 만큼 정확히 읽었다 = 부분 무효화 없음 = 시스템 프롬프트가 두 실행에서 바이트 단위로
동일했다. Risk 카탈로그를 정렬된 순서로 system에 넣은 설계가 의도대로 작동한다.

**주의: 기본 TTL이 5분이다.** 이번 적중은 두 호출이 2분 간격이었기 때문이다.
심사처럼 세션이 띄엄띄엄 들어오면 매번 쓰기(1.25배)만 물고 읽기 혜택이 없다.
`ttl: "1h"`(쓰기 2배, 한 시간 유지)가 유리할 수 있다 — **배포 전 결정할 것.**

`SEMANTIC_VERIFY`의 캐시 prefix가 1,434 토큰으로 Sonnet 4.6 최소 단위(1,024)를
아슬아슬하게 넘겼다. `QuestionGenerator`·`AnswerJudge`는 시스템 프롬프트가 지시문뿐이라
**미달로 캐시가 아예 안 걸릴 가능성이 있다** — F04/F05 실행 시 해당 stage의
`cacheRead`가 계속 0인지 확인할 것.

## 레이턴시

| | v1 | v2(콜드) | v2(콜드) | **v3(웜)** |
|---|---|---|---|---|
| classifier | 16,933 | 15,207 | 18,102 | **10,808** |
| verifier | 5,767 | 12,048 | 5,024 | **4,699** |
| 합계 | 22.7s | 27.3s | 23.1s | **15.5s** |

웜 캐시에서 classifier 10.8초로 **TRD §14 예산(12초) 충족**, 합계 15.5초로
30초 계약 한도에 여유가 생겼다.

**실행 간 편차가 프롬프트 변경 효과보다 크다.** verifier가 같은 프롬프트로
5.0s~12.0s를 오갔다. v2 착수 시 "effort=high 때문에 verifier가 2배가 됐다"고 추정했으나
**틀렸다** — 같은 high effort로 5.0초가 나왔다. **n=1 측정으로 레이턴시를 판단하지 말 것.**
